# v0.2 架构设计：双业态支持

> 状态：**设计稿，待评审**
> 基线：v0.1（tag `v0.1`，commit `e33d1ab`）
> 目标：同一套代码支持两种业态 —— 商场临时停车 / 住宅小区月租年租

---

## 一、为什么要做成「一套代码两个场景」

v0.2 要出两个版本：商场（临时停车为主 + 少量月租）、小区（月租年租为主）。

**两种做法**：

| 做法 | 优点 | 缺点 |
|---|---|---|
| 复制两份项目，各自改 | 起步快，互不干扰 | 两份重复代码；bug 要修两遍；<br>简历上显得是「抄了两份」 |
| **一套内核 + 策略 + 配置** | 差异点集中、代码复用；<br>简历上能讲「可配置的多业态设计」 | 前期要先抽一层抽象 |

**选后者。** 理由：这个项目最终是要写进简历的。招聘方看架构时，
「用策略模式支持两种业态、切换场景只改配置」比「做了两个停车场系统」值钱得多。
而且两个业态的**入场/出场/车位/流水**逻辑其实是同一套，差异集中在「怎么算钱」和「车位归谁」。

## 二、共享内核（两种业态完全复用，不重写）

| 模块 | 职责 | 现状 |
|---|---|---|
| 状态机 | 入场/出场/缴费的流转、在场查重 | v0.1 已有 |
| 车位池 | 分区、类型、归属、占用与释放 | v0.1 已有，需扩展字段 |
| 结算引擎 | 按策略算钱 | v0.1 是硬编码，需抽成策略 |
| 数据层 | 车位、流水读写 | v0.1 是 JSON，需扩表 |
| 流水审计 | 所有动作留痕 | v0.1 已有 |

**关键结论**：状态机、车位池、流水审计这三块**一行都不用重写**，
只需要加字段（车位类型、归属）和换掉结算实现。

## 三、三个计费策略

### HourlyStrategy —— 临时停车（v0.1 现有规则，搬过来）

```
30 分钟内免费
之后 5 元/小时，不满 1 小时按 1 小时算
每天封顶 40 元（跨天按天分段累加）
出场时一次性结算
```

### MonthlyStrategy —— 月租 / 年租

```
入场不产生费用（凭合同免费停）
月租：按自然月或 30 天计费，例 300 元/月
年租：按年计费，例 3000 元/年
周期扣费：到期自动生成应收记录
欠费标记：超过宽限期未缴 → 状态转 overdue
续费：可在到期前续缴，延长到期时间
```

**与 Hourly 的本质差别**：
- 计费触发点不同 —— Hourly 是「出场时」，Monthly 是「周期到期时」
- 钱和「停多久」无关 —— Monthly 按合同周期算，和实际在场时长无关
- 需要「合同」概念 —— Hourly 完全没有

### HybridStrategy —— 商场完整版

```
先看车停在哪类车位：
  · 月租车位 → 走 MonthlyStrategy（免费，验合同）
  · 临停车位 → 走 HourlyStrategy（按小时日计费）
出场时按车位类型分流结算
```

> **注意**：商场场景里同时存在月租和临停车位时，
> 计费不能只看「车在不在场」，得看「车停在哪」。所以车位必须带类型字段。

## 四、场景配置

### 商场场景 `mall`

| 项 | 值 |
|---|---|
| 车位 | A 区 8 + B 区 8 = 16 |
| 其中月租专用 | 3 位（如 A-01~A-03） |
| 临停 | 13 位 |
| 用户档案 | 不需要（临时车主无档案） |
| 计费策略 | Hybrid |
| 额外页面 | 无（v0.1 后台够用） |

### 小区场景 `residential`

| 项 | 值 |
|---|---|
| 车位 | 每户固定车位（示例 8 户 × 1 位）+ 2 位访客临停 |
| 车位归属 | 大部分绑定到具体业主 |
| 用户档案 | 需要：姓名、房号、联系方式、车牌 |
| 合同 | 需要：起止时间、标准、状态（在租/到期/欠费） |
| 计费策略 | Monthly 为主，访客临停走 Hourly |
| 额外页面 | 业主管理、合同管理、续费、欠费催缴 |

## 五、数据模型扩展

**迁移原则**：只加表、不改老字段，v0.1 的 JSON 数据能直接读。

### 现有（v0.1）

```json
// parking.json — 车位
{ "id": "A-01", "zone": "A区", "status": "free", "plate": null, "entryTime": null }

// logs.json — 流水
{ "time": 1792993553950, "type": "in", "plate": "黑A12345", "spot": "A-01" }
```

### 新增字段

```json
// 车位加两个字段
{ "id": "A-01", "zone": "A区", "status": "free", "plate": null, "entryTime": null,
  "kind": "monthly",        // 新增：temp | monthly | reserved
  "owner": null }           // 新增：绑定用户 id

// 新表 users.json — 业主档案
{ "id": "u001", "name": "张三", "house": "3-2-501",
  "phone": "13800000000", "plate": "黑A12345",
  "createdAt": 1792993553950 }

// 新表 contracts.json — 月租合同
{ "id": "c001", "userId": "u001", "spotId": "A-01",
  "kind": "monthly",        // monthly | yearly
  "price": 300, "startAt": 1792993553950, "endAt": 1795585553950,
  "status": "active" }     // active | expired | overdue

// 流水加字段
{ "time": ..., "type": "in", "plate": "...", "spot": "A-01",
  "kind": "monthly",        // 新增：结算方式
  "amount": 0 }            // 新增：月租入场记 0
```

### 数据层要不要换 SQLite？

**建议：暂时不换。** 理由：
- v0.1 用 JSON 是有意的设计取舍（零依赖、可读、易备份）
- 现在数据量小（十几个车位、几百条流水），JSON 完全够
- 换 SQLite 是**架构升级**，属于 v0.3 的事，不该混进 v0.2
- 面试时「为什么一开始用 JSON 后来换 SQLite」本身就是个好答案

v0.2 保持 JSON，但**表结构对齐关系型设计**（users / contracts 分表存储），
这样将来换 SQLite 只是换 `store.py` 的实现，业务层一行不动。

### 策略接口怎么定

```python
# billing.py
class BillingStrategy:
    """计费策略基类。"""
    def quote(self, context) -> dict:
        """算一次应收。

        context 含：spot（车位）、user（业主，可为 None）、
                   contract（合同，可为 None）、minutes（停放分钟）
        返回：{ "amount": 金额, "kind": 结算方式, "detail": 说明文字 }
        """
        raise NotImplementedError


class HourlyStrategy(BillingStrategy):
    """临时停车：按小时与日计费。"""
    def quote(self, context): ...


class MonthlyStrategy(BillingStrategy):
    """月租年租：按合同周期计费。"""
    def quote(self, context): ...


class HybridStrategy(BillingStrategy):
    """商场混合：按车位类型分流。"""
    def quote(self, context): ...
```

## 八、需要你拍板的三个问题

1. **两个场景做成「切换」还是「两个独立入口」？**
   - 切换：一个地址，改配置决定是商场还是小区
   - 独立入口：`/mall` 和 `/residential` 两个 URL，同一个进程里各跑各的
   → 我倾向**独立入口**，演示时不用重启，面试时更有说服力

2. **小区场景的业主档案要不要做登录鉴权？**
   - 做：更真实，但要加 session / 密码管理，工作量 +2~3 小时
   - 不做：后台直接管理业主，专注业务逻辑
   → 我倾向**先不做**，鉴权可以作为 v0.3 的独立议题

3. **年租要不要做？**
   - 做：月租的折扣版，代码上只是 `kind` 不同 + 价格计算，30 分钟的事
   - 不做：先把月租跑通
   → 我倾向**做**，因为「月租年租」是你自己提的需求，缺一半说不过去
